# SeedGen / Moonlight early data reload — isolated Source proposal

The actual client17784 load failed in `MoonlightCachePackCustody.inspect`: the selected `supplementaries:generated_pack` wrapper had a null cached delegate. The installed Moonlight cache directory was present. Read-only comparison found the same73 generated files/53,033 bytes on the client and server, so directory absence was not the observed cause. Native cache `hash.txt` identities legitimately differ between the two endpoints and are not a parity proof or permission to swap caches.

Pinned SeedGen0.9.1 `ClientWorldgen.attempt` constructs a bare `MultiPackResourceManager` at bytecode387, stores it in local9 at390, and immediately reads registries at442/533. It never calls Moonlight's early reload. Moonlight3.7.2 normally hooks `WorldLoader` and `MinecraftServer`, calls `ReloadInstanceWrapper.executeEarlyReloadBlocking(SERVER_DATA, manager, IProgressTracker.createTree(1))`, and synchronously posts `EarlyPackReloadEvent`. Registered native listeners refresh `GlobalCachedStrategy`, prepare providers, run the ordinary generation/reload pipeline and commit cached resources. The missing entry is a concrete lifecycle gap; a sleep would not supply it.

This proposal adds one client-only injection before native bytecode395, after manager construction and before any registry/tag load. It preserves the exact selected pack objects/order, verifies pinned artifacts, requires the normal Moonlight token and completed mod initialization, invokes that native method once, then requires the existing initialized-cache custody check. The original `beforeHybrid`, complete resource attestation, native fingerprints and strict server decision stay unchanged. No direct delegate assignment, cached-file copying, fingerprint substitution, empty-cache inference, NoMod-success fallback, heuristic wait or retry is added.

Root integration, after review:

1. Copy `MoonlightSeedgenEarlyReload.java` to `compat/control-bridge/src/worldfortwo/bridge/` and `SeedgenMoonlightEarlyReloadMixin.java` to its `mixin/` directory. Keep the offline probe out of the runtime artifact.
2. Add `SeedgenMoonlightEarlyReloadMixin` only to the existing CLIENT list in `compat/control-bridge/resources/awft-bridge.mixins.json`. Its exact local table uses the same native attempt as the existing late callback; `CAPTURE_FAILHARD` and `require=1` are retained.
3. Add compile-only `moonlight-1.21.1-3.7.2-neoforge.jar` (2,299,162 bytes/SHA256 `4a9f15108607cc70273f8a0b6eb24e1e99af8eef44bc3ae8681767ca7ce21b0f`) to the existing bridge builder API inputs. Never package upstream classes or generated data. No dependency/catalog/worldgen selection changes are required.
4. Root builds/installs through the existing matched-client/server workflow and owns one real qualification launch. Native early reload may write/regenerate Moonlight's own cache using its normal rules; reserve/storage/lifecycle authority is required before that runtime action. It has NOT been executed by this proposal's tests.

Offline verification command: `python -B compat/proposals/seedgen-moonlight-early-reload-r1/probe.py --home <the existing owned private stage>`. It checks exact native method hashes/order, compiles against the installed pinned Java21/Minecraft/NeoForge/Moonlight APIs, and runs selected-pack identity/order/count/substitution/no-mod-inactive fixtures. It never starts Minecraft, a loader, a native reload, registry generation, networking or a world. The local-table/native exception-scope proof is recorded in `native-api-proof.json`. Earlier compile receipts are retained privately; the final seal names the final successful receipt.

Native qualification remains pending: actual mixin linkage, selected-token eligibility, successful native cache lifecycle, complete post-reload resource attestation, strict client/server terrain equality, and actual DH SeedGen generation/rendering. Moonlight may log/catch a native provider-generation error internally; an initialized delegate or progress tracker alone cannot prove semantic success. Keep those errors visible and retain the strict comparisons. This proposal does not diagnose a new fingerprint difference in advance, and does not prove the owner's visual or frame-time issue resolved.
